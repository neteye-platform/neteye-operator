# ADR-0002: Reconciliation and Resource Application

- **Status:** Accepted
- **Date:** 2026-09-03

## Context

The NetEye Operator converts the desired state in `NetEye` and
`NetEyeTenant` custom resources into Kubernetes resources.

ADR-0001 defines the custom resource API as the supported configuration
interface. Users and external automation must not configure NetEye by changing
resources generated by the operator. The operator therefore needs to correct
drift in the fields that it manages.

The operator must also coexist with Kubernetes API defaulting, admission
webhooks, and delegated operators. These actors can add or update fields that
the NetEye Operator does not own. Replacing a complete resource specification
could remove those fields and cause continuous conflicts between controllers.

Users and automation also need a stable way to determine whether the whole
NetEye installation is ready. At the same time, operators need detailed status
for a component set that will grow during the Kubernetes migration.

## Decision

### Resource application

The NetEye Operator uses Kubernetes Server-Side Apply for resources that it
manages directly.

The operator uses a stable, documented field-manager name. It declares only
the fields for which it owns the desired value. It must not copy the complete
live object into an apply request.

The operator forces ownership of the fields that it intentionally manages.
If another actor changes one of these fields, the next reconciliation restores
the value derived from the NetEye custom resource.

Fields not declared by the operator are preserved. This allows API defaulting,
admission webhooks, and other controllers to manage their own fields. A direct
user change to an unmanaged field may therefore remain, but it is not a
supported NetEye configuration interface and is not guaranteed by the NetEye
API.

The status subresource is updated separately from the desired resource. Status
updates must not rewrite `spec` or metadata owned by another actor.

### Ownership boundaries

The NetEye Operator may force field ownership only after it has established
that the resource belongs to the relevant `NetEye` or `NetEyeTenant`
installation.

If an object with the expected name already exists but the operator cannot
establish that it is owned by NetEye, the operator stops reconciling that
component and reports the conflict. It must not silently overwrite or delete
the object.

Where Kubernetes permits it, generated resources use owner references to the
custom resource that owns them. Resources that cannot use such an owner
reference, including some cluster-scoped or cross-namespace resources, must be
tracked explicitly. Labels alone are useful for identification but are not a
sufficient deletion inventory.

When a resource is removed from the desired state, the operator deletes it only
if it has established ownership and the deletion contract permits deletion.
Deletion must follow ADR-0001 and the component-specific deletion contract.

### Delegated operators

When NetEye delegates a component to another operator, the NetEye Operator
applies the delegated custom resource using Server-Side Apply. It owns only the
fields required to express the NetEye configuration.

The delegated operator owns the resources generated from that custom resource.
The NetEye Operator must not apply, correct, or delete those child resources
directly.

Readiness reported by the delegated operator is translated into the status of
the corresponding NetEye component. The NetEye Operator must not report the
component as ready only because the delegated custom resource was accepted by
the API server.

### Reconciliation behavior

Reconciliation is level-based and idempotent. Each reconciliation compares the
declared NetEye state with the current cluster state and moves the cluster
toward the declared state. It must not rely on having observed every earlier
event.

A successful apply does not by itself mean that a component is ready. The
operator evaluates component-specific readiness after applying resources.

Transient failures are retried through normal controller-runtime behavior.
Failures that require user action remain visible in status and Kubernetes
events until the desired state or the cluster condition changes.

The operator must not use a generic delete-and-recreate fallback when an apply
fails because an immutable field changed. Each such change needs an explicit,
component-specific migration strategy. Until that strategy succeeds, the
component is reported as not ready.

### Status contract

The `NetEye` and `NetEyeTenant` status uses the Kubernetes standard condition
schema.

The top-level `Ready` condition is the stable interface for scripts and users.
It represents readiness of the custom resource as a whole. Consumers must also
compare the condition's `observedGeneration` with `metadata.generation` before
treating it as current.

The top-level status also contains `observedGeneration` and may contain
additional conditions such as `Progressing` and `Degraded`. Condition reasons
are stable, machine-readable identifiers. Messages are concise explanations
for humans and are not a machine-readable API.

Status contains a map keyed by stable logical component names. The map is
dynamic because components will be added as NetEye moves to Kubernetes. Each
entry reports at least its readiness state, observed generation, reason, and a
human-readable message.

Each managed component also reports `resolvedImages`. This is the complete set
of container images selected by the operator for that component. Every entry
has a stable logical name and an exact, digest-pinned image reference. A
component with no container images reports an empty list.

While a component is progressing, `resolvedImages` represents the target set.
When the component is ready, the operator has confirmed that its required
workloads use that set. The field does not attempt to describe every old and
new Pod that can coexist during a rolling update.

For example:

```yaml
status:
  observedGeneration: 4
  conditions:
    - type: Ready
      status: "False"
      observedGeneration: 4
      reason: ComponentsNotReady
      message: Waiting for 1 of 2 components
  components:
    identity:
      status: Ready
      observedGeneration: 4
      reason: Available
      message: Keycloak is ready
      resolvedImages:
        - name: server
          image: ghcr.io/neteye-platform/neteye-keycloak:1.2.3@sha256:<digest>
        - name: configurator
          image: ghcr.io/neteye-platform/neteye-keycloak-configurator:1.2.3@sha256:<digest>
    telemetry:
      status: Progressing
      observedGeneration: 4
      reason: DeploymentNotAvailable
      message: Waiting for the OpenTelemetry Collector Deployment
      resolvedImages:
        - name: collector
          image: ghcr.io/neteye-platform/neteye-otel-collector:0.1.3@sha256:<digest>
```

The exact schema is defined in the CRD and may evolve through normal API
versioning. The following rules remain stable:

- automation that needs whole-installation readiness uses the top-level
  `Ready` condition;
- component keys are logical API identifiers, not Kubernetes object names;
- image names are stable logical identifiers within their component;
- resolved images use complete OCI references pinned by digest;
- adding a new component key is backward compatible;
- callers must tolerate component keys they do not recognize;
- status reports observed state and never becomes an alternative desired-state
  interface.

Kubernetes events and logs provide additional diagnostics, but they are not a
replacement for the status API.

## Alternatives considered

### Replace the complete resource specification

This was not chosen because it can remove defaulted or controller-managed
fields and does not express field ownership precisely.

### Use JSON Merge Patch or update operations

These mechanisms can implement reconciliation, but the operator would need to
maintain more ownership and conflict logic itself. Server-Side Apply provides
field tracking through Kubernetes managed fields and better supports multiple
controllers acting on one object.

### Apply without forcing conflicts

This would make a direct edit or another field manager able to block
reconciliation of a field owned by NetEye. It was not chosen because the
NetEye custom resource is the authoritative desired state.

### Own complete resources instead of selected fields

This would provide a simpler mental model for generated resources. It was not
chosen because even an operator-created resource can contain fields owned by
the API server, admission webhooks, or another controller.

### Report only one global status

This would give scripts a small API but would make failures difficult to
diagnose as the number of components grows.

### Require scripts to inspect every component

This would expose detailed state, but adding a component could break existing
automation. A top-level `Ready` condition provides a stable whole-resource
contract while the component map remains extensible.

## Consequences

The NetEye custom resource remains authoritative for fields managed by the
operator. Drift in those fields is corrected automatically.

Fields added by Kubernetes or cooperating controllers are preserved when they
do not overlap with fields declared by NetEye.

Resource builders must be deliberate about every field they send in a
Server-Side Apply request. Adding a field is an ownership decision and must be
reviewed as such.

The reconciler needs a stable field-manager identity and a reliable ownership
inventory for resources that cannot use owner references.

Name collisions with unmanaged resources fail safely and visibly.

Delegated components retain a clear controller boundary. The NetEye Operator
owns their desired custom resources and observes their readiness, while the
delegated operators own their generated workloads.

Scripts have one stable readiness check based on the top-level `Ready`
condition and `observedGeneration`. Users can inspect the component map to find
which part of the installation is progressing or degraded.

Users and support tools can also identify the exact component artifacts
selected by the operator without inspecting Deployments, Pods, or release
metadata.

Every component needs a readiness definition and, when relevant, an immutable
field migration strategy. This adds component-specific work but prevents a
generic reconciler from making unsafe lifecycle decisions.
